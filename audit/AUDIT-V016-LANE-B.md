## 事项 1 — S14 台架失败（126 PASS + 1 FAIL，S14 verify_rule_domain）

### 裁决：台架问题，不是产品回归。Severity：台架缺陷 P2（发版前必须修台架；产品代码不改）

失败项是 `S14 verify_rule_domain 规则 IP 一致 → rc 0` 这一条断言；`verify_rule_domain` 函数本身与 agent 的 DNS 服务均无回归。

### 证据链

**1. 被测函数在两次台架运行之间字节未变。** 127 PASS 的实施运行 tip 为 `0874b2e`，126+1 的 P1 修复运行 tip 为 `374e7b7`：

```
$ git show 0874b2e:scripts/install.sh | awk '/^verify_rule_domain\(\)/,/^}/' | md5sum
dd2aff976b08baad5b141a9b31e86bb1  -
$ awk '/^verify_rule_domain\(\)/,/^}/' scripts/install.sh | md5sum
dd2aff976b08baad5b141a9b31e86bb1  -
```

`0874b2e..374e7b7` 之间 `scripts/install.sh` 的全部改动就是 P1 两项（`git diff --stat`：`install.sh +77`，`restore-resolv.sh +77`，`stubs/systemctl +27`，另有 `udp_stub_test.go` 与面板 HTML）；`verify_rule_domain`、`serveTCP`、`getent` 相关行零改动。实施方“serveTCP 没动”的辩护方向是对的，但真正的原因不在 serveTCP，而在下面第 2 点。

**2. 变化的是 S14 入口时的 agent 状态——P1(a) 修复本身把它翻转了。**

`verify_rule_domain`（`scripts/install.sh:269-302`）的判定路径是：

```bash
# scripts/install.sh:269-302（摘要）
curl -fsSL -K "$AUTH_CFG" ... "$PANEL_BASE/api/v1/agent/config?server_id=$SERVER_ID" -o "$cfg"
domain=$(sed -n 's/.*"domains":\["\([^"]*\)".*/\1/p' "$cfg" | head -1)
node_ip=$(sed -n 's/.*"node_ip":"\([^"]*\)".*/\1/p' "$cfg" | head -1)
if command -v getent >/dev/null 2>&1; then
  out=$(getent hosts "$domain" 2>/dev/null | awk '{print $1}' | head -1)
```

即：先从 panel 拉规则（不依赖 agent），再用 **`getent` 走系统解析器**判定。S14 在调用前把 `/etc/resolv.conf` 写成 `nameserver 127.0.0.1` + `options use-vc`（`scripts/rig/rig-inner.sh:401`），所以该断言成立当且仅当 **agent 当时正在 `:53` 上监听**。S14 自身从不启动 agent——它隐含假设“S13 的安装留下的 agent 还在跑”。

P1(a)（`e5dafe6`）之前，还原脚本从不停 agent，S13 的两次 `run_restore --yes` 之后 agent 仍在 `:53` 上，S14 通过。P1(a) 之后：

- `scripts/restore-resolv.sh:113-144 record_and_stop_agent()`：还原前记 `AGENT_WAS_ACTIVE`/`AGENT_LISTEN` 并 `systemctl stop dnsunlock-agent`；
- `scripts/restore-resolv.sh:145-170 restore_agent_after()`：`AGENT_LISTEN=:53`（通配符）分支明确**保持停止**（resolved 已重新占住 stub）；
- S13 的安装用的是默认 `--dns-listen :53`，所以 S13 两次还原后 agent 确定性地处于停止状态；
- S14 紧接着在无监听的 `:53` 上做 `getent`，必然 `rc 1`。

台架 stub 也印证了这条链：`scripts/rig/stubs/systemctl` 的 `stop` 分支真杀 agent（按 `$STATE/agent.pid`），`enable`/`start` 分支才调 `start-agent` 真起；`rig-inner.sh` 的 `run_install`/`run_restore` 之外没有任何步骤在 S13 之后、S14 之前启动 agent。

**3. “同跑其他 TCP 项通过”不构成反证。** S0/S1b/S7b 里 `dig @agent` / `getent` 通过时 agent 正在运行；S14 失败时 agent 已被还原停掉——状态不同，比较无效。同样，“容器绿跑里 verify_rule_domain 通过”指的是 P1(a) 之前的运行（agent 未被停），不能用来否定 P1(a) 之后的状态变化。实施方“不是它的改动造成的”这一结论不成立：**正是 P1(a) 的改动（经由 agent 生命周期状态）导致了 S14 翻转**——但这不是产品回归，而是台架 S14 的顺序依赖被 P1(a) 揭了出来。

**4. 排除时序/超时因素。** `verify_rule_domain` 无重试、无等待（单次 `getent`，`curl --max-time 8` 只保护拉配置一步）；失败是确定性的状态缺失（无监听），不是竞态：只要 agent 停着，每次都失败；只要 agent 跑着，每次都通过。S14 前面的 `wait_for_rule`（`rig-inner.sh:95-103`）只在有 agent 的场景里用，S14 没有也不该有——问题不在等待时长。

## 事项 2 — 临时模式重启后状态不 pristine

### 裁决：必须修。Severity：P1（发版阻塞）

`--temp` 宣传的是“重启后失效”，但实际在两条子路径上都不成立；其中一条在重启后会让机器系统 DNS 直接失效，另一条会让临时分流静默变永久，且两种残留都没有任何备份/还原路径可清理。

### 证据链

**前置顺序（`scripts/install.sh`）：`--temp` 的分流发生在 stub 检查与 agent enable 之后。**

```
install.sh:623-644   端口冲突检查：stub_only_conflict 成立且用户确认 → disable_stub_listener
install.sh:775-803   写 /etc/dnsunlock/config.json + systemd unit，systemctl enable --now dnsunlock-agent
install.sh:832-835   TEMP_MODE=1 → apply_temp_dns（才到临时模式分支）
```

**残留 A：持久 drop-in（走 stub 冲突时）。** `disable_stub_listener`（`install.sh:207-222`）：

```bash
mkdir -p /etc/systemd/resolved.conf.d
printf '[Resolve]\nDNSStubListener=no\n' > /etc/systemd/resolved.conf.d/dnsunlock.conf
systemctl restart systemd-resolved
```

这是**永久文件**，与 `--temp` 无关：`apply_temp_dns`（`install.sh:459-486`）既不删除它，也不记录它；还原脚本只有在“存在结构化备份”时才按 stash 逻辑处理 drop-in，而临时模式**不写任何备份**（S4 断言 `S4 未写永久备份`、`S5 未写永久备份`），所以 `dnsunlock-restore-dns` 走到无备份分支时只打印清理提示（`restore-resolv.sh:454-468`，S15），**不会删除该 drop-in**。`disable_stub_listener` 写的 stash（`/etc/dnsunlock/resolved-dropin.absent`）也因此成了死文件，无人消费。

**残留 B：agent 单元是 enable 的。** `install.sh:803` 对临时与永久一视同仁：

```bash
systemctl enable --now dnsunlock-agent
```

unit 文件（`install.sh:786-800`）含 `Restart=always` + `WantedBy=multi-user.target`。`enable` 意味着重启后 agent 自动起、重新占住 `:53`。

**重启后实际状态（按子路径）：**

| 子路径 | 重启后状态 | 用户影响 |
|---|---|---|
| S4 型：resolved 在跑，stub 曾冲突 → 已关 stub + resolvectl 设 DNS | resolvectl 的 DNS 设置随重启消失（符合宣传）；但 drop-in 仍在 → stub 仍关；agent 已 enable → 自启占 `:53`。`/etc/resolv.conf` 若仍是 resolved 的 stub 软链（`127.0.0.53`），该地址上已无监听 → **系统 DNS 直接失效**（`getent hosts example.com` 无结果），直到人工删 drop-in + 重启 resolved 或手动改 resolv.conf（此为按 resolved 常规行为的分析，未在真容器实测——原定 nspawn 补验被安全检查阻塞，见事项 3） | 机器断网式故障：一切域名解析失败，比“临时分流残留”严重得多 |
| S5 型：resolved 未跑 → `write_temp_resolv_conf` 直接写静态 `/etc/resolv.conf`（`install.sh:443-457`，无 chattr 锁但文件本身持久） | 静态文件跨重启保留 `nameserver 127.0.0.1`，agent 已 enable → 自启 → **分流在重启后继续生效**，与“重启后失效”完全相反；且无备份，还原脚本无从还原（S15 只给手动办法） | 临时变永久：用户以为已失效，实际流量仍走 agent/解锁 IP；排障时极难发现 |

两条路径的共同点：**没有任何一个“重启后失效”的承诺由代码保证**——失效的只是 resolvectl 那一小部分，而 drop-in 与 enabled unit 这两个持久化动作发生在临时分支之前、之外。

**台架盲区**：S4/S5 均未触发 stub 冲突（S1b 的 `bindhold` 只在 S1b 存在，`reset_state` 不恢复它），所以台架从未跑过“`--temp` + stub 冲突”的组合；S4/S5 的断言（未写备份、未加锁、输出含“重启后失效”）只验证了宣传文案的输出，没有验证重启后状态。台架无法发现本问题。

### 修复方向（供实施方，不展开设计）

1. `--temp` 模式下**不写持久 drop-in**：stub 冲突时应拒绝并提示改用 `--dns-listen 127.0.0.1:5353`（或自动落到该地址），而不是关 stub；至少要把 `disable_stub_listener` 调用移到永久接管分支之后、并以 `TEMP_MODE` 守卫。
2. `--temp` 模式下 agent **只 `start` 不 `enable`**（或用 `systemd-run --scope` / transient unit），保证重启后不自启。
3. 临时模式应留一份**临时状态记录**（如 `/etc/dnsunlock/temp-state`：原 resolv.conf 内容 + 是否动过 drop-in），让 `dnsunlock-restore-dns` 的无备份分支能真正清理（删 drop-in、停 + disable agent、恢复 resolv.conf），而不是只打印提示。
4. 台架补一个场景：`--temp` + stub 被占 + 模拟重启（或至少断言 `systemctl is-enabled dnsunlock-agent` 为 no 且无 drop-in 文件），否则本修复无法被台架守住。

“只须文档说明”不成立：文档改不了重启后断网的事实；“可以不管”不成立：残留破坏的是系统 DNS 本身，且无自愈路径。

## 事项 3 — 还原“指定监听地址恢复 agent”分支

### 裁决：必须在发版前补真容器验证。Severity：P2（分支本身设计正确、风险有界，但验证缺口必须补；不补不发）

### 分支实现（`scripts/restore-resolv.sh:145-170`，`scripts/install.sh:1140-1165` 内嵌同款，已由 `check-restore-sync.sh` 验明一致）

```bash
# restore-resolv.sh:145-170 restore_agent_after()
if [ "$AGENT_WAS_ACTIVE" != 1 ]; then
  echo "agent 还原前未在运行，保持停止（未改动）。"
  return 0
fi
case "$AGENT_LISTEN" in
  :53|0.0.0.0:53|[::]:53)
    echo "agent 还原前在运行（监听 $AGENT_LISTEN），现保持停止：systemd-resolved 已重新占用 :53（stub 127.0.0.53），agent 的通配符 :53 无法同时绑定。"
    echo "如需继续用 agent 分流，请重新执行安装脚本（它会重新关掉 stub 并接管）；只想恢复系统 DNS 的话，现在已经好了。"
    ;;
  *)
    echo "agent 还原前在运行（监听 $AGENT_LISTEN），正在恢复..."
    if systemctl start "$AGENT_UNIT" 2>/dev/null && systemctl is-active --quiet "$AGENT_UNIT" 2>/dev/null; then
      echo "agent 已恢复运行（监听 $AGENT_LISTEN）。"
    else
      echo "警告: agent 恢复启动失败（监听 $AGENT_LISTEN），系统 DNS 不受影响；请看 journalctl -u dnsunlock-agent" >&2
    fi
    ;;
esac
```

`AGENT_LISTEN` 取自 `/etc/dnsunlock/config.json` 的 `dns_listen`（`restore-resolv.sh:119-122`，解析失败时默认 `:53`——即默认走安全的“保持停止”分支）。

### 风险评估（逐条）

1. **与 resolved 冲突？低。** 指定地址的典型值是 `127.0.0.1:53` / `127.0.0.1:5353`；resolved 的 stub 只绑 `127.0.0.53:53`（及 `127.0.0.54`），地址不同不冲突。病态值 `127.0.0.53:53` 会起不来，但分支有失败警告兜底，且系统 DNS（已还原的 resolv.conf + 已重启的 resolved）不受影响。**结论：冲突风险可接受。**
2. **以错误配置重启？中低。** agent 用安装时写的旧 `config.json` 重启；若用户在安装后改过 panel/token/规则，重启的 agent 仍是旧配置——但这与还原前运行的是同一份配置，还原没有引入新的错误。真正的次生风险在别处：还原后 agent 留在运行态，而 `install.sh` 的重装路径只有 `systemctl enable --now`（`install.sh:803`），对已在运行的 unit 是 no-op、**不重启**——用户随后重装会以为新配置生效，实际跑的仍是旧 agent 进程。这是还原分支与安装路径的交互缺口，P3，建议发版后修（重装时若 unit 已 active 应 `restart`），本次不阻塞。
3. **“已恢复运行”的断言太弱？中。** 分支只验 `systemctl is-active`，不验端口、不验解析。agent 可能处于 `active` 但 crash-loop（unit 含 `Restart=always`）、或绑端口失败反复重启，而还原脚本已向用户报告成功。后果有界：系统 DNS 已还原走上游，坏的只是分流悄悄失效——用户会误以为分流还在。建议补验时把“`dig @127.0.0.1 -p <port> tiktok.com` 返回规则 IP”作为恢复成功的判定条件之一（或至少在文档里写明自测命令）。
4. **违背用户“还原=停掉 agent”的预期？低（设计如此）。** 分支语义是“恢复还原前状态”，输出里写明了在恢复；用户若只想恢复系统 DNS，agent 多跑一个监听不影响系统 DNS。但应在还原输出里加一句“agent 仍在运行（监听 …），如需彻底停用请 `systemctl disable --now dnsunlock-agent`”，避免用户误以为还原=卸载。

### 验证缺口（为什么必须补）

- 台架 S11（`rig-inner.sh:307-324`）确实用 `--dns-listen 127.0.0.1:15353` 走过该分支，但**没有任何断言验证恢复结果**：既没有 `markers_has "start dnsunlock-agent"`，也没有还原后 `dig @127.0.0.1 -p 15353 tiktok.com` 返回规则 IP 的断言，更没有“resolved stub `127.0.0.53:53` 与 agent `127.0.0.1:15353` 共存”的断言。所谓“rig stub 层覆盖”只是“代码被执行过”，不是“行为被验证过”。
- 真 systemd 下未验证的关键点 stub 模拟不了：`systemctl start` 后 resolved 是否真已重新占住 stub、agent 是否真绑上指定地址、两者是否都答、以及 `is-active` 通过时 agent 是否真在服务。

### 补验要求（发版前必须做；本审计已备好容器与面板，但未执行——见“执行阻塞”）

在带真 systemd + 真 systemd-resolved 的 nspawn 容器内（非 chroot stub 台架）：

1. 安装 agent `--dns-listen 127.0.0.1:53`，走永久接管（含关 stub），确认 `getent hosts tiktok.com` 返回规则 IP；
2. 跑 `dnsunlock-restore-dns --yes`，确认退出码 0、`resolv.conf` 恢复原内容；
3. 断言三点同时成立：`systemctl is-active dnsunlock-agent` 为 active；`dig @127.0.0.1 tiktok.com A` 返回规则 IP（agent 真在服务）；`dig @127.0.0.53 example.com A` 有结果（resolved stub 真回来了，两者共存）；

## 附加发现 S9b — 还原清理断言与产品语义矛盾（台架问题）

### 裁决：台架断言错误，不是产品回归。Severity：台架 P2（与 S14 同批修台架）

两次全量重跑均失败：`S9b 清理：还原回 hpve 文件`（`scripts/rig/rig-inner.sh:299`）：

```bash
run_restore "$LOG/s9b-restore.log" --yes
assert "S9b 清理：还原回 hpve 文件" files_eq /etc/resolv.conf "$RIG/fixtures/resolv.conf.hpve"
```

但还原的文档语义是“`--yes` 默认还原**最早的一份**（原始状态）”（`scripts/restore-resolv.sh:344`，`CHOSEN="${DIRS[0]}"`，glob 字典序最小=最旧时间戳）。S9b 时备份已有 8 份，最早的是 S1b 的 pre-takeover 备份（`resolv.conf.base`，`198.19.0.1`），不是 S9b 当次的 hpve 备份（`1.1.1.1`）。run 1 的 `s9b-restore.log` 原文：

```
可用的备份（时间倒序）：
  [1] 2026-11-21T11:28:36+0000  pre-takeover  DNS: 1.1.1.1 1.0.0.1   /var/lib/dnsunlock/backup/20261121-112836_pre-takeover
  ...
非交互模式：默认还原最早的一份（原始状态）: /var/lib/dnsunlock/backup/20261121-112416_pre-takeover
已还原 /etc/resolv.conf <- /var/lib/dnsunlock/backup/20261121-112416_pre-takeover/resolv.conf
```

还原按设计正确返回了原始 base 文件；断言期待 hpve 是错的——它假设 `--yes` 还原到“紧邻的上一个状态”，与其他所有清理场景（S3/S6/S7b/S11/S13 均断言还原回 base 文件）自相矛盾。选择逻辑在 `0874b2e`（127 PASS 的 tip）与现 tip 的独立版、内嵌版里完全一致（均为 `CHOSEN="${DIRS[0]}"`），故该失败与 P1 修复无关，是台架自带的断言缺陷。

修复：S9b 清理改用 `--backup <本次 pre-takeover 备份>`（即 `newest_backup` 在还原前的值）显式还原并断言 hpve；或改断言为还原回 base 文件（与 S3 等一致）。前者更能验证“hpve 场景可还回 hpve”这一本意。
